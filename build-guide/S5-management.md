## ① 목적과 완료 조건

진료 뒤의 일 — 수납 · 청구 · 회계 · 인사급여 · 자재(ERP), 인수인계 · 근무표 · 결재(Clinic), 직원 교육 · 이수증(edu) — 을 HIS 에 붙입니다. 세 시스템 모두 **HIS 직원 명부와 로그인**에 기대므로, 직원 한 명의 입사 → 변경 → 퇴직이 여러 시스템에 어떻게 전해지는지 이 단계에서 맞춥니다.

완료 조건:

- [ ] ERP 가 떠 있고, 연동 주소 · 로그인 신뢰 도메인을 자기 기관 값으로 바꿨다
- [ ] 🔴 청구 관련 결정(`legal.claimStatusAccuracy` · `policy.copay.rounding`)을 기록했다
- [ ] 🔴 청구 · 자격조회의 **대체 경로**(기존 청구 소프트웨어 또는 기관이 붙이는 전송 모듈)를 정했다
- [ ] Clinic 이 HIS 직원 · 조직을 동기화했다
- [ ] edu 의 배포 형태를 정했고, 설정 화면의 연결 점검을 통과했다
- [ ] 직원 입사 · 변경 · 퇴직이 각 시스템에 반영되는 경로를 확인했다

설치 때 알아 둘 것:

- **ERP DB 확장** — 마이그레이션이 PostgreSQL 확장 `btree_gist` · `pg_trgm` 을 만듭니다. DB 계정에 확장 생성 권한을 주거나 미리 만들어 둡니다. 마이그레이션은 기동할 때 적용됩니다.
- **ERP 와 HIS 의 DB 공유** — 저장소에는 HIS 와 같은 PostgreSQL · Redis 를 함께 쓰는 배치 구성이 있습니다. 한 DB 서버를 여러 시스템이 나눠 쓰면 **연결 수 한도도 나눠 씁니다.**
- **ERP 따라가기에서 확인한 것**(2026-09-14 · 기준 커밋 · 새 설치본 · 외부로 나가지 못하는 네트워크)
  - 원본 파일 그대로 이미지 빌드(core · 워커 2 · 웹)와 기동이 성공했습니다. core 가 기동할 때 마이그레이션을 적용해 **12개 스키마 220개 테이블**을 만듭니다.
  - 운영 compose 에는 **DB 컨테이너가 없습니다** — HIS 서버의 PostgreSQL 에 ERP 전용 DB(`erp`)와 역할(`erp_app`)을 먼저 만들고 `DATABASE_URL` 로 가리킵니다.
  - 🔴 **`ENV` 는 정확히 `prod`** 로 둡니다. 다른 값(예: `production`)이면 운영용 안전 점검(자리표시 비밀값으로 기동 금지)과 세션 쿠키의 `Secure` 속성이 켜지지 않는데, 경고 없이 기동합니다.
  - 🔴 **ERP 에는 첫 관리자를 따로 만드는 절차가 없습니다.** 계정은 **HIS 로그인에서 넘어올 때 이메일로 자동 생성**됩니다(HIS `ADMIN` → ERP `ADMIN` · 그 밖의 역할 → `STAFF` · 이미 있는 계정은 역할 유지). 그래서 **HIS 를 먼저 세우고 아래 SSO 를 연결해야** ERP 를 쓸 수 있습니다.
  - JWT 비밀은 파일(`secrets/jwt_secret`)로 주입하고, 암호화 키 `DATA_ENC_KEY` · 전화번호 색인 키 `PHONE_BIDX_KEY` 는 서로 다른 값으로 새로 만듭니다.
- **Clinic DB 변경** — 로컬 상태 저장 테이블은 저장소의 SQL 스크립트로 추가됩니다. 적용 순서를 확인합니다. 서비스 전용 태그가 없으므로 설치본은 커밋 해시로 고정합니다.
- **edu 따라가기에서 확인한 것**(2026-09-14 · 기준 커밋 · 새 설치본 · 외부로 나가지 못하는 네트워크)
  - 원본 파일 그대로 이미지 빌드(API · 웹)가 성공했습니다(약 3분 20초 · 이 PC).
  - 운영 compose(`infra/docker/docker-compose.prod.yml`)는 **HIS · sign · AI 와 같은 호스트의 호스트 네트워크**를 전제로 하고, API · 웹이 코드에서 `127.0.0.1` 에만 붙습니다. 컨테이너 네트워크로 나눠 두려면 웹과 앞단 프록시가 API 와 네트워크를 함께 쓰게 구성해야 합니다.
  - 🔴 **운영 설치 순서** — 기관 설치 안내 문서의 순서(기동 → 스키마 반영 → 콘텐츠 시드)만으로는 API 가 DB 에 붙지 못합니다. 운영 compose 는 앱 전용 DB 역할(`edu_app` · 행 단위 보안 적용 대상)로 접속하고, 기동 때 기관(테넌트) 목록을 읽기 때문입니다. 확인한 순서:
    1. `.env.prod` 작성(`EDU_DB_PASSWORD` · `EDU_APP_PASSWORD` 새로 생성 · `HIS_JWT_SECRET` = HIS `AUTH_SECRET` · `HIS_SERVICE_SUB` = HIS 의 실제 관리자 사용자 id)
    2. 기동 → `npx prisma db push --skip-generate`(스키마)
    3. `node prisma/seed-tenants.js`(기관 행) → `node prisma/apply-rls.js`(앱 DB 역할 · 행 단위 보안 36개 테이블) → API 재기동
    4. 콘텐츠 시드 `seed-curriculum` → `seed-legal-content` → `seed-pdf-summaries` → `seed-exam-questions` → `seed-onboarding`
  - `seed-tenants.js` 는 **기관 식별자(slug)를 코드에 고정**해 만듭니다. 기관명은 `EDU_ORG_NAME` 으로 들어갑니다.
  - `seed-pdf-summaries.js` 는 새 설치본에서 **차시(모듈)가 없는 과정 3개**를 만나면 그 자리에서 멈춥니다. 과정 코드를 하나씩 넘겨 돌리면 나머지 13개는 들어갑니다(16개 중 13).
  - 연결 시험(새 설치본끼리 · `검증됨` 2026-09-14): HIS 화면의 **사내교육** 단추 → edu 관리자 홈 · edu 설정 화면 연결 점검 HIS = 공개키 1개 · **직원 명부 동기화 56명 = HIS 재직 직원 기록 56명** · edu 에서 이수 처리 → HIS 직원 교육 기록 생성.
  - HIS 설정 **`edu.url`** 에 edu 주소를 넣은 뒤, HIS 통합 설정 목록(`/api/v1/config?category=integration`)에 `edu.url` 이 보이는지 **먼저 확인**합니다. 보이지 않으면 사내교육 단추를 누르기 전에 설정을 바로잡습니다(`확인 필요(따라가기)` — 화면에서 바로잡는 방법).
  - 따라가기에서 확인한 직원 진입 경로는 **HIS 화면의 사내교육 단추**입니다. edu 자체 로그인 화면(아이디 · 비밀번호)은 `구현·미검증` 으로 둡니다.
  - HIS → edu 직원 이벤트 웹훅은 HIS 가 리허설 모드에서 보내지 않아 따라가기에서 확인하지 못했습니다(리얼 전환 리허설 대상).
- **edu DB 격리** — 새 테이블을 만들 때마다 행 단위 보안(RLS) 적용 절차를 따릅니다(스키마 반영 명령은 RLS 를 붙이지 않습니다). 운영에서 스키마 반영은 이미지를 다시 빌드한 뒤에 합니다.

### 로그인 방식 — 시스템마다 다릅니다

| 시스템 | HIS 신원을 확인하는 방식 | 관리할 것 |
|---|---|---|
| edu | 직원 로그인은 HIS 가 발급한 토큰을 **공개키(JWKS)** 로 검증 · 직원 명부 조회와 이수 기록은 **HIS 서명 비밀키(`AUTH_SECRET`)를 공유**해 edu 가 만든 서비스 토큰으로 호출 | HIS 공개키 주소 · 🔴 공유 비밀키 보관 · 교체 |
| ERP | **공유 비밀키** 서명 — HIS 와 ERP 가 같은 비밀키를 가짐 | 🔴 비밀키 보관 · 교체를 따로 관리 |
| Clinic | **API 키** — Clinic 에서 범위를 지정해 발급한 키를 HIS 에 등록 | 키 발급 · 보관 · 교체 |

### ERP

- 🔴 **설정 기본값에 특정 설치본의 연동 주소가 들어 있습니다.** HIS · Clinic · sign · AI Server 연동 주소와, 패스키 로그인의 신뢰 도메인(RP ID) · 오리진을 자기 기관 값으로 바꿉니다. Clinic 쪽 설정 예시에서 확인된 주소 · 오리진 키는 **`MAIN_APP_URL` · `NEXT_PUBLIC_MAIN_URL` · `NEXT_PUBLIC_MAIN_APP_URL`**(병원 웹) 과 **`AUTH_ALLOWED_ORIGINS`**(인증 구성요소)입니다(2026-09-12 기준 커밋 확인). **패스키 RP ID 키는 설정 예시 파일에 없습니다** — 코드 안에 있는지, 다른 곳에서 읽는지는 `확인 필요(따라가기)`.
- 비밀값은 서버의 환경 파일에만 둡니다.
- 웹은 `/erp` 하위 경로로 서비스합니다. 앞단 프록시가 랜딩 응답을 캐시하지 않게 둡니다.
- **HIS → ERP 직원 SSO**(연결 표 `검증됨` 2026-09-14 · 새 설치본끼리) — HIS 와 **같은 호스트의 `/erp`** 로 묶어야 합니다.
  - 앞단 프록시 세 갈래: `/erp/`(정확히) → ERP core `/`(SSO 랜딩) · `/erp/api/` → core `/api/`(앞의 `/erp` 제거) — 두 곳 모두 `X-Forwarded-Prefix: /erp` 와 **포트까지 포함한 `Host`** 를 넘깁니다 · 그 밖의 `/erp/` → ERP 웹(앞의 `/erp` 유지).
  - ERP `HIS_JWT_SECRET` 에 **HIS API 의 `AUTH_SECRET` 과 같은 값**을 넣습니다.
  - 따라가기에서 끝까지 확인한 조합: HIS 설정 **`erp.handoff` = `cookie`** + ERP **`HIS_JWT_AUDIENCE=erp-sso`**. HIS 화면의 `ERP` 단추 → ERP 대시보드로 들어가고, ERP 에 계정이 자동 생성됐습니다. 같은 SSO 토큰을 다시 쓰거나, 만료되거나, 서명이 틀린 토큰은 거부됐습니다.
  - ERP 에 들어갈 수 있는 사람 = HIS **`erp.allowedRoles`**(기본 `ADMIN`) ∪ **`erp.allowedUserIds`**(HIS `접근 권한 관리` → 외부 시스템 접근). 위 조합에서 허용 밖 사용자는 HIS 가 403 으로 막고, 개별 허용 목록에 넣으면 들어갑니다(따라가기 확인). ERP 명단을 이 목록으로 자동으로 보내는 호출은 아직 없어 사람이 넣습니다.
- **ERP → sign 외주 계약 서명 · sign → ERP 완료 통지**(연결 표 `검증됨` 2026-09-15 · 새 설치본끼리) — 따라가기 순서:
  1. sign 환경변수 `ERP_API_KEY`(소비자 `erp`) · `ERP_WEBHOOK_SECRET` 과 ERP `SIGN_API_KEY` · `SIGN_WEBHOOK_SECRET` 을 같은 값으로(기관마다 새로 생성). ERP `SIGN_INTERNAL_BASE` 는 `/v1` 까지.
  2. 🔴 ERP **`ATTACHMENT_DIR`**(계약 PDF 보관 경로 · 영속 볼륨)을 설정합니다 — 운영 compose 와 환경 예시에 없고, 없으면 서명 요청이 "첨부 저장소 미설정"으로 멈춥니다.
  3. ERP `SIGN_CALLBACK_URL` 은 **sign 서버가 https 로 닿는 ERP 주소**(`…/api/v1/integrations/sign/webhook`)이고, `SIGN_PORTAL_BASE` 는 거래처가 여는 sign 포털 주소입니다. 둘 다 기본값이 다른 설치본 주소이므로 반드시 바꿉니다.
  4. 확인 — ERP 계약 등록 → 서명 요청(계약 PDF) → 거래처 포털 링크 → 거래처 서명 → ERP 계약 서명 상태 `COMPLETED`. 틀린 서명의 완료 통지는 ERP 가 **403 으로 거부**합니다(따라가기 확인). 거래처 링크를 보내는 자동 발송은 없어 담당자가 전달합니다.
- **HIS → ERP 약품 보험코드 매핑 반입 — 연결 표 `검증됨`(2026-09-15).** ERP 약제팀이 확정한 HIS 약품 코드 ↔ 보험 제품코드를 HIS 가 가져와 약품 마스터에 채웁니다(관리자 실행 · 이벤트 전달을 켜면 매일 새벽 자동). 따라가기에서는 ERP 확정 매핑을 가상으로 넣어 **반영 1 · HIS 에 없는 코드 보고 1 · 형식이 틀린 보험코드 반영 안 됨 · 키가 틀리면 `ERP_403` 사유로 반영 0** 을 확인했습니다. 새 설치본의 ERP 에는 확정 매핑이 없고, ERP 가 매핑 후보를 만들려면 청구 라인과 약가 마스터가 먼저 있어야 합니다.
- **ERP → HIS 검진권 딜러 정산 지급 회신 — 연결 표 `검증됨`(2026-09-15).** ERP 가 딜러 지급을 마치면 HIS 정산을 `PAID` 로 바꿉니다. 🔴 ERP 쪽 **송신 스위치 · HIS 주소 · 연동 키 · 본문 서명 비밀값이 모두 기본으로 비어 있고**, HIS 는 기본으로 **서명을 강제**합니다 — 스위치만 켜고 서명 비밀값을 빼면 모든 회신이 401 로 거절돼 정산이 멈춥니다. 네 값을 함께 넣습니다(HIS 에 재무 웹훅 비밀값을 따로 두지 않으면 ERP 연동 키가 서명 비밀값으로 쓰입니다). 따라가기에서 서명 없음 · 틀린 서명 · 틀린 키가 모두 401 로 막히고, 올바른 서명 회신은 지급액 · 원천징수와 함께 한 번만 반영되는 것을 확인했습니다. ERP 가 HIS 를 부를 수 있는 주소는 이 경로도 코드에 고정된 목록뿐입니다.
- **ERP → HIS 의료진 계약 서명 발의 — 연결 표 `검증됨`(2026-09-15).** ERP 가 의료진 계약의 서명을 요청하면 HIS 가 계약 문서를 발급 · PDF 로 렌더해 sign 에 서명 요청을 만듭니다. 이 연결은 **전용 키**(HIS `erp.signOriginationKey` ↔ ERP 발의 키 — 웹훅 키와 별개)를 씁니다. 🔴 **HIS 의 PDF 렌더 서비스가 떠 있어야 합니다** — 없으면 HIS 가 사유 없이 500 을 돌려줍니다. 따라가기에서 발급 · 렌더 · sign 요청 생성 · ERP 계약 "서명 요청됨" 과, 틀린 키 401 · 재요청 시 봉투 중복 없음을 확인했습니다. 서명 완료 뒤 ERP 계약이 발효되고 완료본을 가져오는 구간은 HIS 이벤트 전달(리얼 모드)이 먼저라 아직 확인하지 않았습니다.
- **HIS → ERP 운영 이벤트 · 진료비 계산서**(따라가기 2026-09-15 · 운영 이벤트는 일부만 확인 — 연결 표 `구현·미검증`)
  - 🔴 HIS 설정 **`erp.webhookEnabled` 는 설치 뒤 꺼져 있습니다.** 켜기 전에는 수납 · 청구 · 재고 · 인사 이벤트가 ERP 로 보낼 대기열에 **쌓이지도 않습니다**. `erp.webhookUrl` 을 넣는 것만으로는 이벤트가 가지 않습니다.
  - 켠 뒤에도 HIS 가 **리허설 모드이면 이벤트를 보내지 않고 대기열에 보류**합니다(발송 기록을 "보냄"으로 바꾸지 않음). 따라가기에서 장비 점검 불합격 1건이 올바른 ERP 경로로 쌓이고 보류되는 것까지 확인했고, 실제 발송은 리얼 전환 뒤에 확인합니다. **보류된 이벤트는 리얼로 바꾸는 순간 나갑니다** — 리허설 중 만든 시험 이벤트는 전환 전에 정리합니다.
  - 수납 화면의 **ERP 진료비 계산서**(연결 표 `검증됨` 2026-09-15)는 ERP 에 진료 라인이 쌓여야 금액이 나옵니다. 라인이 없으면 "진료 라인 없음"으로 표시되고, ERP 키가 틀리면 사유(`ERP_403`)가 그대로 보입니다. 차트번호 없이 방문 번호만으로 조회하면 ERP 가 거절합니다(`ERP_422`).
  - **전환 · 리허설 때 진료 라인 채우기 — ERP → HIS 청구 라인 백필(연결 표 `검증됨` 2026-09-15).** ERP 관리자 기능이 HIS 의 기간별 수납 라인을 가져와 적재합니다(다시 실행해도 중복 없음). 따라가기에서 HIS 수납 9항목이 ERP 라인 9개로 들어갔고, **ERP 계산서 합계가 HIS 수납 합계와 같았습니다**. 같은 경로로 미청구 진행분 · 재료 마스터 · 재원 환자일도 가져옵니다.
  - 🔴 **HIS 기본 시드의 수납 6건은 ERP 가 받지 않습니다**(처방 코드가 아닌 값이 코드 칸에 들어 있음 — ERP 가 사유를 남기고 거부). 시험 수납은 코드가 있는 처방으로 새로 만듭니다.
  - 🔴 기간 끝 날짜는 **그날 0시까지**로 해석됩니다 — 오늘 수납까지 받으려면 끝 날짜를 다음 날로 줍니다.
  - 🔴 ERP 가 HIS 를 부를 수 있는 주소는 **코드에 고정된 목록**(한 운영 도메인 · 같은 호스트)뿐입니다. 다른 도메인이면 코드 수정 또는 같은 호스트 배치가 필요합니다(사번 매핑과 같은 제약).
- **HIS 직원 셀프서비스 → ERP 조회**(연차 잔여 · 급여명세 등 · 따라가기 2026-09-15 에서 **2개 조회만 확인** — 연결 전체는 `구현·미검증`) — HIS 설정 `erp.webhookUrl` 에 **ERP 기준 주소만**(`/api/v1` 없이 — HIS 가 경로를 붙입니다) · `erp.integrationKey` ↔ ERP `HIS_WEBHOOK_KEY` · HIS `ess.targetTokenSecret` ↔ ERP `ESS_TARGET_TOKEN_SECRET` 를 같은 값으로. ERP `ESS_TARGET_TOKEN_ENFORCE` 는 **기본 꺼짐**이라, 켜야 연동 키만으로 다른 직원의 급여를 조회할 수 없습니다(따라가기: 켠 상태에서 다른 직원 대상 · 만료 · 다른 키 서명 요청이 모두 거부됨). ERP 에 **HIS 와 같은 사번의 직원**이 있어야 값이 채워집니다.
- **LIS → ERP 검사 청구 · LIS → PACS 병리 뷰어 링크**(연결 표 `검증됨` 2026-09-15) — LIS `ERP_BILLING_URL`(ERP `…/api/v1/integration/lis/billing`) · `ERP_BILLING_SECRET` ↔ ERP `LIS_BILLING_SECRET`. 검사 결과가 확정되면 LIS 가 청구 항목을 **캡처만** 하고, ERP 로 보내는 것은 **전송 단계**(LIS 관리자 `POST /api/v1/billing/transmit` 또는 주기 작업)입니다. ERP 는 받은 청구를 적재하지만 **수가 마스터가 비어 있으면 금액을 산정하지 못합니다** — 수가 반입 뒤에 확인합니다. 서명 · 시각이 틀린 청구는 ERP 가 403 으로 거부합니다(따라가기 확인).
- **ERP → HIS 직원 사번 매핑**(따라가기 부분 확인) — 🔴 ERP 는 HIS 주소를 **코드에 고정된 허용 목록**으로만 부릅니다. 다른 호스트의 HIS 를 부르려면 코드 수정이 필요합니다(따라가기에서는 ERP 와 같은 호스트의 localhost 로 흉내 냄). 또 매핑 백필은 **Clinic 사용자 ID 로 직원을 짝지으므로 Clinic 연동이 먼저** 돼 있어야 대상이 생깁니다.
- **ERP → HIS 수가 마스터 반입**(따라가기 부분 확인) — ERP 가 수가 · 치료재료 마스터를 HIS 로 올리는 경로는 **운영자가 돌리는 스크립트**입니다. 🔴 기준 커밋에서는 이 스크립트가 **ERP 운영 이미지에 들어 있지 않고**, 보낼 수 있는 HIS 주소가 **코드에 고정**(설정으로 못 바꿈)돼 있어 다른 기관은 코드 수정 없이 쓸 수 없었습니다. HIS 쪽 수신(수가 코드 일괄 등록)은 따라가기에서 맞물리는 것을 확인했습니다. 그 전까지 HIS 코드 마스터는 [S1](S1-core-his.md) 의 반입 절차로 채웁니다.
- **ERP → AI 청구 사전심사 · 공시 검색**(따라가기 확인) — 🔴 기준 커밋에서는 ERP 가 부를 수 있는 AI 주소가 **코드에 고정**돼 있어, 원내 AI Server 로 설정하면 **ERP 자체 검색으로 조용히 넘어갑니다**(화면의 출처 표시가 `local`). 출처 표시를 확인하고, 원내 AI 를 쓰려면 ERP 프로젝트와 먼저 협의합니다.
- **ERP → AI 공시 색인 보내기**(따라가기 2026-09-15 · 일부만 확인 — 연결 표 `구현·미검증`) — ERP 가 보험 · 수가 공시를 AI Server 에 등록 · 폐지하는 경로도 **AI 주소가 코드에 고정**돼 있어, 원내 AI Server 주소로는 보낼 수 없습니다(코드 수정 필요). 또 공시를 실제로 보내는 **ERP 연동 워커 컨테이너에는 AI 주소 · 키 설정이 들어가지 않아** 설치 뒤 보내기 작업이 대기 상태로 남습니다 — 설정을 넣을 때 core 와 연동 워커 양쪽을 확인합니다. 시험용으로 주소 제한만 풀었을 때 등록 · 폐지 · 틀린 키 거부 · 내용 해시가 다르면 거부 · 전화번호 모양이 든 공시는 보내지 않음이 동작했고, 색인 완료는 이 PC 의 AI 에 임베딩 모델이 없어 확인하지 못했습니다.
- 설치 뒤 재무 · 물류 등 **정기업무 담당 역할**을 배정합니다. 역할 보유자가 없으면 알림이 관리자에게 갑니다.

  - 웹훅 구독은 HIS API `POST /api/v1/clinic/webhooks/subscribe`(수신 주소 · 이벤트 · 서명 비밀값)가 Clinic 에 등록하는 방식입니다. 이 호출을 부르는 화면과, 들어온 웹훅을 HIS 가 어디서 검증하는지는 `확인 필요(따라가기)`.

- 설정 탭: 갱신 주기(3초 미만 값은 기본값으로 바뀜) · 알림 종류별 사용 여부.

### edu

- **배포 형태를 먼저 정합니다.** 단독 배포는 환경변수의 HIS 가 곧 인증원입니다. 멀티테넌트는 기관마다 자기 HIS 주소를 넣어야 로그인이 열리고, 새 기관 설정은 플랫폼 콘솔에서 넣습니다.
- 연동 준비: HIS(로그인 공개키 · 인사 · 이수 기록 · 직원 웹훅 서명) · sign(이수증) · AI Server(문항 · 요약 · 학습 도우미 · 전사) · 알림 채널(Clinic 경유). 설정 화면의 **연결 점검**으로 확인합니다.
- **edu → sign 이수증 서명 · sign → edu 완료 통지**(연결 표 `검증됨` 2026-09-15 · 새 설치본끼리) — 따라가기에서 확인한 순서:
  1. sign 관리 API(`sign-admin` 키)로 **소비자 `edu` 를 등록**하고 `requests:write` · `certificates:write` 를 줍니다. edu 는 sign 환경변수로 심는 소비자가 아닙니다. 🔴 **이름을 `edu` 로** 둡니다 — sign 이 완료 통지를 서명할 비밀값을 `<소비자 이름>_WEBHOOK_SECRET` 규칙으로 찾으므로, 이름이 다르면 HIS 용 비밀값으로 서명돼 edu 가 받지 않습니다.
  2. 같은 비밀값을 sign `EDU_WEBHOOK_SECRET` 과 edu `EDU_WEBHOOK_SECRET` 에 넣습니다(기관마다 새로 생성).
  3. edu 소비자 키로 **등록자 인증서**를 발급받고(`POST /v1/certificates/enroll`) 그 일련번호를 edu `SIGN_REGISTRAR_SERIAL` 에, 키를 `SIGN_API_KEY` 에 넣습니다. 기관마다 따로 발급합니다.
  4. 🔴 **sign 은 운영 설정에서 https 콜백만 받습니다.** edu 는 콜백 주소를 **`EDU_PUBLIC_URL` + `/api/v1/webhooks/sign`** 으로 만들므로, `EDU_PUBLIC_URL` 은 **sign 서버가 https 로 닿는 주소**여야 합니다. 원내 사설 인증서를 쓰면 sign 이 그 CA 를 신뢰하게 합니다(따라가기: 사설 CA 로 edu 앞에 TLS 중계를 두고 sign 에 `NODE_EXTRA_CA_CERTS`). 같은 값이 직원 화면 링크에도 쓰이므로 직원 브라우저와 sign 서버가 **같은 주소로 닿게** 구성합니다.
  5. 확인 — 이수 처리(또는 관리자 재발급) → edu 이수증 `ISSUED` → sign 검증 주소에서 문서 무결성 `VALID` → sign 로그 `request.completed` 전송 성공 · edu 로그 "sign 통지로 인증서 확정". 틀린 서명의 통지는 edu 가 **받기만 하고 반영하지 않습니다**(2xx 로 답하므로 sign 쪽에는 실패가 보이지 않습니다 — edu 로그를 봅니다).
  - edu 설정 화면의 sign **연결 점검**은 sign 이 404 를 돌려줘도 "정상"으로 표시했습니다(따라가기) — 점검 통과만 믿지 말고 위 5번으로 확인합니다.
- 콘텐츠 저장: 기본값 `storage.archive` 가 `none` 이라 로컬에만 저장합니다. 수료증 · 이수 자료가 들어가므로 백업을 따로 준비하거나 아카이브를 설정합니다. 캐시 삭제는 기본 꺼짐(`storage.cacheMaxBytes` 0)입니다.
- 기본 콘텐츠는 초안 · 검수 상태로 들어 있습니다. 병원의 임상 검수와 병원 고유 정보 입력(온보딩 자료의 자리표시)을 거친 뒤 노출합니다.

## ⑥ 아직 안 되는 것과 대체 수단

| 아직 안 되는 것 | 대체 수단 |
|---|---|
| 🔴 **청구 · 자격조회 대외 전송** 모듈이 구현돼 있지 않습니다. HIS 는 보험 청구서 작성(EDI 서식)까지 합니다. `integ.hiraSubmit` 은 구현 여부를 읽으므로 미완으로 남습니다 | 기존 청구 소프트웨어와 함께 쓰거나 기관이 전송 모듈을 붙입니다 |
| `integ.eligibility` 는 설정값만 읽습니다. 자격조회 전송 모듈은 구현돼 있지 않습니다 | 🔴 판정 유형이 **`EXTERNAL`**(바깥에 맡긴 항목)이고, 판정 근거가 **설정 한 줄**(`eligibility.mode` 를 `NHIS` 로 둔 것)입니다. 즉 **모듈 없이 설정만 바꿔도 이 항목은 초록이 됩니다.** 담당은 원무이고, 실제 상태는 **연동 개통 게이트**(`/admin/integration-gates`)에서 확인합니다 → [게이트 화면](../screens/his.md#구축을-진행하는-세-화면). 설정값을 바꾸기 전에 **실제로 조회가 나가는지**를 먼저 봅니다 |
| ERP 는 국내 제도(심사 · 고시 · 수가 · 세법 · 노동)를 전제로 설계했습니다 | 다른 나라는 청구 · 세무 · 급여 규칙을 새로 붙입니다 |
| 심사 결과 통보서 파서 · 삭감 위험 평가 보정은 실제 자료가 있어야 진행됩니다 | 기관이 확보한 자료로 착수합니다 |
| ERP → HIS 재고 입고 · 자산 코드 매핑 · 청구 심사결과 콜백 · 환자 조회 경로는 `미구현` 입니다(HIS 가 받을 준비만 됨) | 해당 업무는 각 시스템 화면에서 따로 처리합니다 |
| ERP → Clinic 근태 수집 · ERP → sign 일반 전자계약 · edu → HIS 인앱 알림 · HIS → Clinic 열람 로그인 티켓은 `미구현` 입니다 | 근태는 ERP 쪽 입력, 계약은 트랙 A, 알림은 Clinic 경유, 결재 문서는 Clinic 에 따로 로그인해 봅니다 |
| Clinic 병원 서비스의 워크그룹 · 동선 데이터 경로는 `판정 불가`(배포 구성에 따라 다름)입니다 | 따라가기에서 배포 구성으로 확인합니다 |
| Clinic 은 HIS 자료를 받지 못하면 예시 데이터로 채웁니다. 혼잡도 임계값은 저장되지만 판정에 쓰이지 않고, AI 지식 기능은 구현이 없습니다 | 화면의 출처 배지를 확인합니다 |
| edu 로그인은 HIS 로그인뿐입니다. HIS 자격(면허) 이벤트는 반영하지 않고, 외부 콘텐츠 업체 연동은 표준(xAPI) 수신만 있습니다 | HIS 없이 edu 만 따로 쓰지 않습니다. 면허 관리는 HIS 에서 합니다 |
| edu 의 감사 해시체인은 한 프로세스를 전제로 합니다 | API 서버를 여러 개로 늘리지 않습니다 |
| ERP 의 AI 보조는 신고 금액을 확정하지 않습니다(초안까지) | 법정 신고는 사람이 확정합니다 |

## ⑦ 흔한 함정

- **ERP 공유 비밀키를 한쪽만 바꾸는 것.** HIS 와 ERP 가 같은 값을 가져야 합니다.
- **DB 확장 권한 없이 ERP 마이그레이션을 돌리는 것.**
- **ERP `ENV` 를 `prod` 가 아닌 값으로 두는 것.** 운영 점검이 조용히 꺼집니다.
- **HIS 와 ERP 를 한 호스트 · 한 네트워크에 둘 때 서비스 이름을 그대로 쓰는 것.** 두 compose 모두 `web` · `redis` 가 있어 앞단 프록시가 엉뚱한 쪽으로 붙을 수 있습니다. 컨테이너 이름을 고유하게 가리킵니다.
- **정기업무 담당 역할을 배정하지 않는 것.** 모든 알림이 관리자에게 몰립니다.
- **ERP 시드의 개발용 로그인 계정을 남기는 것.** 시드는 합성 데이터(`TEST-` 접두)이고 개발용 계정이 들어 있습니다. 실운영 전에 지웁니다 → [S8](S8-go-real.md).
- **edu 야간 동기화를 끄는 것.** 신규 입사자가 직원 이벤트만으로 반영되지 않는 경우가 있습니다.
- **edu 이수증을 개별 폐기 외의 방법으로 지우는 것.** 개별 이수증 폐기는 `withdraw` 로만 합니다. 공유 등록자 인증서를 폐기하면 발급 전체가 무효가 됩니다.
- **edu 웹훅 수신에서 오류 코드를 돌려주는 것.** 항상 2xx 로 답하고 미반영 사유는 본문에 적습니다(저장소 규칙).
- **Clinic 화면의 예시 데이터를 실제 자료로 믿는 것.**
