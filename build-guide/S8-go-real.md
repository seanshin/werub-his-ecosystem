> ⚠️ 초안 — **새 설치본으로 한 번 따라가 본 결과를 반영했습니다**(2026-09-13~16 · 개발 PC 한 대 · arm64 · 8GB 가상 머신 · GPU 없음 · 외부로 나가지 못하는 네트워크). 남은 `확인 필요(따라가기)` 표시는 x86 · GPU 기준 장비나 사람 결정이 필요한 곳입니다. · 기준 2026-09-11 · [가이드 목차](README.md)

## ① 목적과 완료 조건

리허설을 끝내고 실환자를 받습니다. 순서는 **가상 데이터 격리 → 키 · 인증서 새로 만들기 → 실데이터 이관 → 리얼 빌드 배포 → 개시 확인**입니다. 리얼 전환 뒤에는 시험용 통로가 원천적으로 없어야 합니다.

완료 조건:

- [ ] 🔴 결정 등록부의 **개시 전 필수 11개**가 모두 기록됐다(아래 표)
- [ ] 🔴 Go-Live 의 **개시 차단 31개**를 하나씩 확인했고, 준비되지 못한 항목의 사유와 대체 수단을 기관 문서에 남겼다
- [ ] 🔴 가상 병원 시드 · 데모 · 시험 데이터를 **모든 시스템에서** 제거하거나 격리했다
- [ ] 🔴 리얼 빌드를 배포했다(Go-Live `security.hisMode`)
- [ ] 기관 기본정보(요양기관 기호 · 사업자등록번호 · 대표자 등)를 인허가 값으로 확정했다
- [ ] 개원일을 확정하고, **진료 · 청구 실왕복 1건**으로 개시를 확인했다

## ② 설치 — 전환 절차

### 1. 전환 전 확인

| 확인 | 어디서 |
|---|---|
| 개시 전 필수 결정 11개 기록 | `/admin/decisions` |
| 개시 차단 31개 상태 | `/admin/go-live` |
| 최근 암호화 백업 | Go-Live `security.dbBackup`(정기 백업만 셈) |
| 감시자 판정 | `/admin/sentinel` |

**백업 → 복원 시험**(따라가기 2026-09-15 · 새 설치본 · 가상 데이터) — HIS 저장소의 백업 스크립트와 같은 방식으로 떠서 **다른 DB 서버에 복원**했습니다. 운영 DB 에는 절대 복원하지 않습니다.

1. 백업: `pg_dump --no-owner --no-privileges --format=plain` → `gzip` → `gpg --symmetric --cipher-algo AES256 --passphrase-file <파일>`(패스프레이즈 파일은 권한 600 · 백업과 다른 곳에 보관)
2. 복호: `gpg --batch --decrypt --passphrase-file <파일> -o restore.sql.gz <백업>.gpg` — 틀린 패스프레이즈는 복호가 거부됩니다
3. 복원: **새로 띄운 같은 판본의 PostgreSQL**(따라가기는 네트워크 없는 컨테이너)에 `gunzip -c restore.sql.gz | psql -d restore_test`
4. 대조: 모든 테이블의 행 수 · 인덱스 수 · 확장 목록을 원본과 비교합니다

따라가기 결과: 덤프 3초 · 압축 · 암호화 뒤 약 0.45MB(시드 규모) · 복원 5초 · 오류 0 · **테이블 562개 행 수 일치**(백업 뒤 새로 쓰인 감시자 기록 표 하나만 차이) · 인덱스 1,604개 · 확장 일치. 규모가 다른 기관 데이터의 소요 시간은 기관이 다시 잽니다.

- 🔴 **HIS 백업 스크립트는 HIS DB 하나만 뜹니다.** 같은 PostgreSQL 서버에 ERP DB 를 함께 두는 배치라면 ERP 는 따로 백업해야 합니다. 스크립트 안의 경로 · DB 이름 · 사용자도 기관 값으로 바꿉니다.
- PostgreSQL 16.10 이후의 `pg_dump` 는 덤프 첫머리에 `\restrict` 줄을 넣습니다. 복원에 쓰는 `psql` 도 같은 판본 이상이어야 합니다.

### 2. 가상 데이터 격리 — 시스템마다

| 시스템 | 무엇을 정리하나 | 근거 |
|---|---|---|
| HIS | 가상 병원 시드 · 데모 · `TEST-` 픽스처(Go-Live `flag.demoSeedPurge`) · 데모 날짜 롤포워드 끄기(`dev.demoDateRoll` = `false`) | Go-Live |
| LIS | 운영은 `starter` 시드 · 파일럿 데이터 정리 API(요청 → 승인 두 단계) — **따라가기에서 끝까지 실행**(아래) | LIS 릴리즈 요약 · 따라가기 |
| ERP | 합성 시드(`TEST-` 접두) · **시드에 든 개발용 로그인 계정** | ERP 릴리즈 요약 |
| sign | 저장소 문서의 **초기화 절차** — 테스트 데이터와 CA 를 새로 만듭니다. 이때 **연동 시스템이 보관한 인증서도 다시 발급**받습니다. 키 보관 장치 전환 · 본인확인 사업자 연결 · 연동 키 교체도 이 시점에 함께 하도록 짜여 있습니다 | sign 릴리즈 요약 |
| 환자 앱 | 배포 빌드에서는 시드 환자용 시험 계정 안내가 나오지 않는 조건이 걸려 있습니다 — 배포 빌드로 확인 | 환자 앱 릴리즈 요약 |
| PACS · edu · twin · cerno · Clinic | 리허설 데이터 정리 방법 — PACS · edu · twin · cerno 기준 커밋에는 **정리 전용 스크립트가 없습니다**(파일 이름 purge · cleanup · reset · wipe 검색 0 · 2026-09-13). DB 를 새로 만들지, 표를 골라 지울지는 `확인 필요(따라가기)` | 각 저장소 기준 커밋 |

HIS 는 **첫 관리자 계정도 기본 시드로만 만들 수 있어서**([S1](S1-core-his.md#설치-순서)), 리얼 전환 전에 기관 관리자 계정을 따로 만들고 시드 계정 88개를 정리하는 순서가 필요합니다. HIS 도 기준 커밋에 **시드 정리 스크립트 파일이 없습니다.** Go-Live 의 `flag.demoSeedPurge` 는 **수동(MANUAL) 항목**이고(담당 전산 · 원무 · 확인 화면 `데이터 품질` · 설명 "데모 환자 · 리허설 결재 · LIS 종단검증 픽스처 파기 · LIS 회신 수신 후 실행"), 정리 명령과 순서는 `확인 필요(따라가기)`. 리허설에 쓴 직원 · 시험 계정의 정리도 같은 시점에 합니다. 각 시스템의 계정 · 세션 회수를 따로 확인합니다(시스템마다 회수 방식이 다릅니다 — 따라가기에서 절차 확정).

**LIS 리허설 데이터 정리 — 따라가기에서 실행한 순서**(2026-09-15)

1. `GET /api/v1/admin/seed-cleanup/real-data` — HIS 연동으로 들어온 리허설 환자 · 오더는 **시드로 등록되지 않아 "실데이터"로 감지**되고 정리가 막힙니다. LIS 설치 문서는 "신규 사이트는 설치 시점부터 추적되므로 해당 없다"고 적지만, **HIS 와 연결해 리허설한 신규 사이트는 해당됩니다.**
2. 백필 `POST …/seed-cleanup/backfill` — 리허설 데이터를 정리 대상으로 **등록만** 합니다(삭제 없음). 확인 문구와 **다른 관리자**를 승인자로 요구합니다. 🔴 실환자 데이터가 섞인 DB 에서는 실행하지 않습니다.
3. `GET …/preview?batch=site-pilot` → 확인 문구(`site-pilot N건 삭제`) → `POST …/request`
4. **다른 관리자가 자기 계정으로** `POST …/approve/:runId` — 요청자 본인 승인은 거부됩니다(따라가기 확인)
5. `real-data` 가 `clean: true` 인지 확인 · 리허설 계정은 사용자 관리에서 **비활성화**(정리 API 는 계정을 지우지 않습니다)

따라가기: 12건 등록 → 12건 삭제 → 실데이터 0 · 마스터와 관리자 계정 보존.

**리얼 전환 직전에 볼 것 — 보류된 발송.** HIS 는 리허설 모드에서 외부로 보낼 연동 이벤트를 **보내지 않고 대기(PENDING)로 둡니다.** 이 대기분은 **리얼 모드가 되는 순간 그대로 나갑니다.** 전환 직전에 연동 대기열(`integration_outbox` 의 PENDING)을 확인하고, 리허설 때 생긴 이벤트는 정리합니다(따라가기 설치본은 0건 — 웹훅 구독을 만들지 않았음). 문자 · 메일은 대기열 없이 보내는 순간 막히므로 이 문제가 없습니다.

리얼 모드 전환 자체(빌드 · 배포)는 따라가기에서 **실행하지 않았습니다** — 남은 `확인 필요(따라가기)` 는 **"실제로 전환하면 무엇이 일어나는가"** 입니다. 전환이 **어떻게 판정되는지**는 기준 커밋 코드에서 확인했습니다(2026-09-16).

| 코드가 말하는 것 | 기관에 무슨 뜻인가 |
|---|---|
| 모드는 개발 · 리허설 · 리얼 **세 단계이고 리얼이 가장 제한이 세다** | 리얼은 "푸는" 모드가 아닙니다 — 시드 로그인 · 시드 배지 · 개발용 비밀 폴백이 모두 닫힙니다 |
| 실효 모드 = **빌드 상한과 관리 화면 설정 중 더 제한적인 쪽** | 관리 화면 설정은 빌드 상한보다 넓힐 수 없습니다. 반대로 **리허설 빌드에 리얼 설정을 주면 실효는 리얼**입니다 |
| 🔴 모드 환경변수가 **비어 있으면 리얼** | 모드를 정하지 않은 설치본은 리얼로 돕니다([⑦ 흔한 함정](#⑦-흔한-함정)) |
| 모드 조회에 실패하면 기본값으로 번역하지 않고 **빌드 모드를 그대로** 쓴다 | 장애가 모드를 넓히지 않습니다 |

그래도 **직접 돌려 보기 전에는 알 수 없는 것**이 남습니다 — 전환 순간 대기열이 실제로 어떻게 나가는지 · 화면에서 무엇이 사라지는지 · 전환 뒤 처음 도는 대외 발신이 어디까지 가는지.

**전환 뒤에 처음으로 확인할 수 있는 연결** — 아래는 리허설 모드에서는 나가지 않아 따라가기에서 확인하지 못한 것들입니다. 전환 직후 **한 건씩 실제로 돌려 보고 확인일을 기록**합니다(S7 「연결 확인 기록」 표를 그대로 씁니다).

| 무엇 | 전환 뒤 확인할 것 |
|---|---|
| HIS → ERP 운영 이벤트(수납 · 청구 · 재고 · 인사 · 서명 완료) | 대기열의 이벤트가 ERP 에 도착하는지 · ERP 가 처리하지 못한 이벤트를 어디에 쌓는지 |
| ERP 진료비 계산서 · 약품 코드 확정 | 이벤트가 쌓인 뒤 금액이 채워지는지(그 전에는 "진료 라인 없음") |
| ERP 의료진 계약 발효 · 서명 완료본 회수 | 계약 서명이 끝났을 때 ERP 계약이 발효되고 완료본이 첨부되는지(회수 주소는 코드에 고정돼 있어 ERP 협의가 필요할 수 있습니다) |
| HIS → edu 직원 이벤트 웹훅(입사 · 변경 · 퇴직) | 직원 변동이 edu 에 바로 반영되는지(그 전에는 야간 동기화에 의존) |
| 환자 문자 · 메일 · 알림 | 리허설에서 모의 처리되던 발송이 실제로 나가는지 · 수신자가 맞는지 |

🔴 **전환 순간에 한꺼번에 나갑니다.** 위 확인을 하기 전에 **대기열 정리(바로 위)** 를 먼저 끝냅니다.

### 3. 키와 가명화

- **개인식별정보 암호화 키** — 운영 키가 자리표시 값이 아닌지 Go-Live `security.encryptionKey` 가 판정합니다. 키 파생을 통일하고 키 교체를 언제 할지는 결정 `security.keyDerivationUnify`(시드 정리와 함께 · 지금 · 실환자 등록 직전까지 보류)로 정합니다.
- **환자번호 가명화 컷오버** — Go-Live `cutover.phase0.pseudonym`(법무 · CPO 승인과 실행 기록 · `/admin/phase0-cutover`).
- **데이터 보유 · 실파기 개시** — Go-Live `legal.retention`(법무 승인).

### 4. 실데이터 이관

- 기존 시스템에서 환자 · 진료 · 원무 데이터를 옮기는 도구와 절차는 공개 자료에 없습니다 — `확인 필요(따라가기)`.
- ERP 는 전환 때 HIS 의 청구 라인 · 미청구 진행분 · 재원 정보를 **일괄 적재**하는 경로가 있습니다(`구현·미검증`).
- v4.12.0 이전 HIS 데이터를 가져오는 경우 여권 · 외국인등록번호 암호화 백필이 필요하고, 여권번호 검색이 정확 일치로 바뀝니다(HIS 릴리즈 요약).

### 5. 리얼 빌드 배포

- Go-Live `security.hisMode` 는 **빌드의 운영 모드 상한**을 읽습니다. 관리 화면에서 설정만 바꿔서는 이 항목이 끝나지 않고, 리얼 빌드를 배포해야 끝납니다.
- 리얼 빌드는 배포 스크립트에 **모드를 명시해서** 만듭니다 — `./infra/scripts/deploy.sh --all --mode real`([S7 에 사용법](S7-rehearsal.md)). 🔴 **`--mode` 를 생략하면 서버의 현재 값(리허설)을 그대로 이어받습니다.** 개시 배포에서는 반드시 명시합니다.
- **시험 계정이 산출물에 남았는지는 가드 테스트가 봅니다.** HIS 웹에는 *"테스트 계정은 운영 번들에 실리지 않는다"* 는 테스트가 있어, 소스 트리를 훑어 테스트 계정 목록이 운영 빌드에 들어갈 수 있는 자리에 있는지 검사합니다. 이 테스트가 남긴 문장이 규칙을 그대로 말합니다.

  > **"숨긴 것과 없는 것은 다른 사실이다. 조건부 렌더만 하면 번들에 남아 그대로 검색된다."**

  실제로 2026-08 에 로그인 화면 두 곳이 테스트 계정 목록을 그리고 있었고, 공용 비밀번호가 소스에 문자열로 남아 있었으며, **목록 정본이 두 벌**이었습니다. 그래서 진입점을 **빌드 때 접히는 상수 분기 안의 지연 로딩 하나로 좁히고**, 그 구조가 유지되는지를 테스트로 고정했습니다 → [취지 8](../overview/02-principles.md).
- 시드 데이터가 남았는지는 별도 항목입니다(아래 시드 정리). 새 기관의 배포 경로 구성은 `확인 필요(따라가기)`.

### 6. 개시

- `open.opening.date` — 개원일을 확정합니다. 🔴 확정 전까지 시스템은 어떤 절대 날짜도 계산에 쓰지 않습니다.
- `open.opening.confirm` — 🔴 "설정을 켰다"가 아니라 **"실제로 한 바퀴 돌았다"**를 확인합니다(진료 · 청구 실왕복 1건).

## ⑦ 흔한 함정

- **설정 화면 토글만으로 리얼이 됐다고 믿는 것.** Go-Live 는 빌드의 상한을 읽습니다. 리얼 빌드를 배포해야 합니다.
- 🔴 **운영 모드를 아예 안 정하는 것.** 모드 환경변수가 **비어 있으면 리얼로 동작합니다**(기준 커밋 코드). 비밀·시드 쪽으로는 안전한 기본값이지만, **"아직 안 정했으니 리허설이겠지"는 틀립니다.** 개발기와 리허설기는 모드를 **명시**합니다.
- **배너가 사라진 것을 전환 실패로 읽는 것.** 리얼에서는 상단 배너를 **일부러 띄우지 않습니다** — 상시 배너는 곧 읽히지 않게 되고, 그러면 리허설 배너까지 같이 안 보이게 되기 때문입니다. 전환 확인은 배너가 아니라 **시드 로그인 단추가 사라졌는지 · 모드 조회 응답**으로 합니다.
- **모드 배너가 이상할 때 화면만 다시 켜 보는 것.** 화면은 모드 조회에 실패해도 **기본값으로 번역하지 않고 빌드 모드를 그대로 씁니다**(장애가 모드를 넓히지 않게). 그러니 배너가 예상과 다르면 **모드 조회 응답(`/api/v1/mode`)부터** 봅니다.
- **"리얼이 되면 발신이 켜진다"고 읽는 것.** 리얼은 발신이 **나갈 수 있는 상태**일 뿐이고, 채널마다 세 조건(구현 + 설정 + 승인)은 그대로 남습니다. 반대로 **리얼이 아니면 설정과 무관하게 나가지 않습니다** — 리허설 중 실제 문자가 환자에게 가는 사고를 막는 장치입니다.
- **시드 정리 전에 실환자를 등록하는 것.** 가상 데이터와 실데이터가 섞이면 되돌리기 어렵습니다.
- **리허설 CA · 인증서를 운영에 가져가는 것.** sign 을 초기화하면 연동 시스템의 인증서도 다시 발급받아야 합니다.
- **ERP 시드의 개발용 로그인 계정을 남기는 것.**
- **개원일을 확정하지 않는 것.** 확정 전까지 시스템은 절대 날짜를 계산에 쓰지 않습니다.
- **"설정을 켰다"를 개시 확인으로 삼는 것.** 진료 · 청구 실왕복 1건이 확인입니다.
- **"기록 없음"을 "미완료"로, "결정함"을 "적용됨"으로 읽는 것.** 개원 단계와 결정 등록부는 이 둘을 따로 보여 줍니다.
- **리허설에 쓴 계정을 남기는 것.** 각 시스템의 계정 · 세션 회수를 시스템별로 확인합니다.
